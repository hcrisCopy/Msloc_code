# 训练流程讲解：从一条 proposal 到一次参数更新

[返回主 README / 文档导航](README.md#navigation) · [单卡运行路线](README.md#single-gpu) · [多卡运行路线](README.md#multi-gpu) · [Ray 同步细节](Ray多角色训练.md) · [面试自测](第二阶段Qwen面试问题清单.md)

**本文解释算法和口头讲解顺序，不是执行命令清单。** 单卡也可以理解并在资源允许时验证 SFT / OPSD / GRPO；只有多 Trainer 才能实测 DDP，只有将角色分配到不同 GPU 后才能讨论跨 GPU 并行收益。讲解时将“已跑出的单卡结果”和“待多卡验证的实现”分开。

以下对应当前 demo 与固定的 ms-swift 4.5.3 实现。数值例子用于手算，**不是已经跑出的实验结果**。原有面试问题清单仍可搭配阅读。

## 先讲输入、权重与目标

假设 proposal 是原视频 `[100,140]` 秒，与某段异常的最长交集为 `[110,125]` 秒。模型接收该 proposal 的 40 帧，定位目标为相对区间 `[10,25]`，不是原视频的绝对时间，也不是超出 proposal 的完整 GT。若没有任何异常交集，该 proposal 的目标为 real，即使原视频其他地方有异常。

视频使用原项目 16/8/16 非均匀采样；`.timestamps.json` 保存实际相对时间。学生输入是视频、任务格式和片段时长。OPSD 教师额外获得真假标签、相对 GT、类别及解释要点。GRPO 的 GT 和标注解释交给奖励函数，不能放进学生提示词。

默认权重流程与正式实验相同：SFT 训练语言 LoRA；将 SFT LoRA 与原始底座 merge，得到固定教师；OPSD 学生继续训练原 SFT LoRA；GRPO 再继续训练 OPSD LoRA。视觉编码器和对齐层始终冻结。merge 只用于导出教师，不替换学生正在训练的 LoRA。

## SFT：对标准回答做监督

1. 从 fake proposal 构造标准回答：标注解释的一句或三句，加相对定位区间。
2. 输入 prompt 与标准回答，通过 teacher forcing 一次前向计算每个回答 token 的条件概率。
3. 对有效回答 token 做交叉熵；提示词和 padding 不作为回答监督。
4. 反向传播、梯度累积、优化器更新；默认只更新语言 LoRA。

令标准回答为 `y*`，主要目标为：

\[
L_{SFT}=-\frac{1}{N}\sum_{t\in有效回答位置}\log p_\theta(y_t^*\mid x,y_{<t}^*).
\]

它训练模型“在标准前缀后面接标准 token”。当前 SFT 仅有 fake，不保证模型已经学会正常片段的 real 输出。32 步只是训练流程演示，不能凭 loss 下降认定定位能力已改善。

## OPSD：在学生自己的前缀上向教师学习

### 训练前与训练中是两种不同计算

**训练前预检**：学生用普通提示词完整生成，教师用特权提示词完整生成，比较分类、格式和定位；再筛选教师正确的样本。这一步证明特权信息在选定样本上确实帮助了教师。

**训练中的每一步**：教师不需要另生成一个完整答案。先由学生生成，再把同一份学生回答接到教师提示词后面，教师通过前向计算给每个位置的“下一个 token 分布”。

### 一次更新的数据流

1. 从筛选后的 proposal 读取普通输入 `x` 与特权输入 `x⁺`。
2. 学生按当前策略采样完整回答 `y`，temperature=1。生成阶段不建立用于优化的长反向图。
3. 学生对 `x+y` 做带梯度前向，得到回答位置的词表分布 `S_t`。
4. 固定教师对 `x⁺+y` 做无梯度前向，得到同一学生前缀下的分布 `T_t`。师生提示词长度不同，要对齐回答位置，不能按整个输入的绝对 token 下标直接比较。
5. 对有效回答位置计算完整词表的 Jensen–Shannon divergence，求平均。
6. 反向传播，只更新学生；下一轮由更新后的学生重新生成。

本 demo beta=0.5：

\[
M_t=0.5S_t+0.5T_t,
\qquad
L_{OPSD}=\frac{1}{N}\sum_t\left[0.5D_{KL}(T_t\Vert M_t)+0.5D_{KL}(S_t\Vert M_t)\right].
\]

`lmbda=1` 表示使用学生 on-policy rollout，`sft_alpha=0` 表示不另外叠加 SFT CE；这里的 beta 是分布混合系数，与 GRPO 的 KL 系数不是一回事。框架按有效 token 做损失归一化，再由 Trainer 完成累积与分布式更新。

例如在某位置只有两个候选 token，学生分布 `[0.8,0.2]`、教师 `[0.2,0.8]`，混合分布 `[0.5,0.5]`，该位置 JSD 约为 `0.193` nats。优化推动学生接近教师的偏好。真实训练比较完整词表，不只是两个候选，也不只是已采样 token 的概率。

### 必须能解释的限制

- 教师看到 GT，但未必每次正确，所以先验证、再筛选。教师预检更好也不保证所有学生错误前缀上的教师分布都更好。
- 教师不能把已经写出的前缀“删除”。它只能对后续 token 给出分布；梯度更新改变的是以后生成时的策略。
- 数字不是必然按一位一位分词。“下一个 token 是 2、再接 9”的设想必须以实际 tokenizer 为准，不能按字符推导训练行为。
- GT `[10,25]` 是特权输入，不等于自动把教师分布强制设成正确答案。这里没有额外的硬约束解码。
- 教师参数固定，但其输出随学生前缀变化，这是条件输入变化，不是教师正在训练。
- on-policy 的“on”指前缀来自当前学生；实际优化是 rollout 之后的可微前向，不对采样操作本身反向传播。

## GRPO：用同组回答的相对好坏更新策略

### 1. 同一输入生成 4 个回答

每个 proposal 用相同普通输入生成 4 次，temperature=0.8、top_p=0.95。全局 batch=8 表示本次更新共有两个 proposal 的两组回答，不是八个 proposal 每个再乘四。

### 2. 解析并计算三项奖励

总奖励为：

\[
R=R_{loc}+0.1R_{format}+0.3R_{explanation}.
\]

定位奖励沿用 `Qwen/grpo_rewards.py`：

| 情况 | 定位奖励 |
|---|---|
| real，正确输出 real | 1 |
| real，却输出 fake | -1 |
| real，格式不可解析 | -0.5 |
| fake，未正确解析为 fake | -1 |
| fake，解析到区间 | `0.25 + 0.55×IoU + 0.20×matched_boundary − 0.25×unmatched` |

最后一项中，无交集时 `matched_boundary=0, unmatched=1`；有交集时用原 Trace 的边界分数，`unmatched=0`。格式奖励：可解析为 fake/real 得 1，否则 -1。

解释奖励只在 GT 为 fake、回答正确解析为 fake 且 IoU≥0.30 时计算；其他情况为 0。冻结的 CPU NLI 模型比较生成解释与标注事实：`graph_recall − 0.5×contradiction`。它评价标注事实的覆盖和矛盾，不代表已经验证回答中的所有额外细节。real 的正常描述不获得此项解释奖励。

### 3. 每组独立计算优势

\[
A_i=\frac{R_i-\bar R}{s_R+10^{-4}}.
\]

该版本组内标准差使用 PyTorch 默认样本标准差。假设四个总奖励为 `[0,0,1,1]`，均值 0.5、样本标准差约 0.577，优势约为 `[-0.866,-0.866,0.866,0.866]`。优势是同组相对分数，不是绝对正确概率。

四个回答奖励一样时，优势为 0，奖励驱动的策略梯度没有区分方向；KL 项仍可能产生梯度。这也是报告里 `frac_reward_zero_std` 值得看的原因。GRPO 不另外训练一个 value/critic 模型来估计该 baseline。

### 4. 计算回答 token 的概率、比值和 KL

对已经生成的回答重新前向，取得当前策略选中 token 的 log probability `log pθ`，以及生成/旧策略的 `log pold`；固定参考策略提供 `log pref`。参考策略是本次 GRPO 开始时的模型，不是 OPSD 的特权教师。

\[
\rho_{i,t}=\exp(\log p_\theta(y_{i,t})-\log p_{old}(y_{i,t})).
\]

当前设置只有一次策略更新，初始概率比常接近 1；不要因此认为策略梯度为 0。分母不反向传播，分子仍有梯度。具体是否缓存旧概率由框架的 old-policy 路径决定。

KL 使用选中 token 的估计而不是 OPSD 那种完整词表 JSD：令 `d=log pref−log pθ`，主要形式是 `exp(d)−d−1`。该版本为数值稳定先将 d 限制在 `[-20,20]`，再将估计限制在 `[-10,10]`；代码讲解时应与这一实现保持一致。

### 5. 构造损失、反向传播、更新

省略 mask 和上述数值裁剪后，GRPO 目标可写成：

\[
L=-\frac1G\sum_i\frac1{|y_i|}\sum_t
\left[\min(\rho_{i,t}A_i,\operatorname{clip}(\rho_{i,t},0.8,1.2)A_i)
-0.02\widehat D_{KL,i,t}\right].
\]

当前 `loss_type=grpo` 按回答的有效 token 长度归一化，再平均回答。每条回答的组内优势用于其各个有效 token；不是每个 token 单独运行 NLI 获取一个奖励。默认只更新语言 LoRA，奖励函数、NLI 和参考模型不更新。

奖励函数不需要可微：它给出的标量通过优势乘上可微的策略概率项产生学习信号。梯度不会穿过字符串解析、IoU 或 NLI 奖励计算。

## 加速究竟加在哪里

| 工作 | Transformers 基线 | vLLM demo |
|---|---|---|
| 学生 rollout | Transformers 生成 | vLLM 生成 |
| OPSD 教师前向 | 固定教师 | 同样的固定教师 |
| 学生训练前向、反向、优化器 | HF Trainer | HF Trainer |
| GRPO 奖励 | 原奖励函数、CPU NLI | 相同 |
| 生成权重同步 | 同一模型直接使用 | 更新后同步到 vLLM |

因此实际收益取决于 rollout 占比、生成长度、同步开销和奖励开销。比如 NLI 占据主要耗时，单独加速 rollout 不会让整个训练等比例变快。监测里的 `generate_including_sync` 含同步，loss forward 包含教师/参考的相关计算，阶段时间有重叠，不能相加成总时间。

`ray_launch.py` 已将这些工作拆成常驻 Actor：生成、固定教师／参考模型、CPU 奖励、DDP 训练。每轮先验证版本 v，生成与评分完成后做一次更新，再将 v+1 权重分块同步给全部生成 worker，校验内容和前向概率，才允许下一轮。并发发生在同轮的独立请求、角色副本以及 GRPO 参考／奖励计算之间；没有跨轮异步 rollout。

Ray 多卡对比固定八卡角色分配：serial Transformers→parallel Transformers 测并发派发，parallel Transformers→parallel vLLM 测生成后端。使用 [Ray 八卡对比](Ray多角色训练.md#multi-benchmark)中的三组命令和报告；权重传输、校验与保存开销也计入 step 周期。单卡 Ray 只有一个 Trainer，不执行 DDP，重点讲角色通信和权重同步，不用它证明八卡加速。代码实现与目标服务器实测应分开陈述，尚未运行的部分不能说成已取得加速。
